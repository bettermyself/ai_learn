### 1. 核心原则 (Core Principles)

在多终端环境中使用 Claude Code 进行并行任务时，首要目标是防止干扰。

- **界限清晰 (Scope Defined)**：确保“主对话”与“分支对话”的职责范围明确。
- **最小重叠 (Minimal Overlap)**：代码变更应尽量避免重叠。
- **任务正交 (Orthogonality)**：选择互不相关的任务并行处理，从根本上消除冲突的可能性。



### 2. 推荐工作模式 (Preferred Pattern)

建议采用 **“主更副查”** 的模式：

- **主窗口 (Main Chat)**：专注于实际的代码更改和核心开发任务。
- **分支窗口 (Forks)**：用于只读或辅助性任务，不直接修改代码。例如：
  - 询问关于当前代码库状态的问题。
  - 调用外部服务进行调研（如拉取文档）。
  - 搜索 GitHub 寻找可参考的开源库。
  - 其他通用性研究。



### 3. 终端数量管理 (Terminal Management)

- **拒绝盲目堆砌**：不建议盲目追求终端数量（如 Boris Cherny 提到的 5 本地 + 5 上游的配置）。
- **MVP 原则 (Minimum Viable Parallelization)**：
  - 只有在真正必要时才增加终端或实例。
  - 如果脚本能解决，就用脚本；如果能在主会话中通过 `tmux` 解决，就不要新开终端。
  - **新手建议**：先熟练掌握单实例管理，再尝试并行。
  - **通常用量**：大多数情况下，2-3 个实例足矣，总终端数控制在 4 个左右。



### 4. 规模化与代码隔离 (Scaling & Git Worktrees)

当必须运行多个涉及代码修改的实例时，**必须**使用 Git Worktrees 以物理隔离工作环境。

**操作规范：**

1. **使用 `/rename`**：为每个 Claude 会话命名，避免混淆（e.g., `/rename feature-login`）。

2. **使用 Git Worktrees**：

   ```bash
   # 为并行任务创建独立的工作树 (Worktrees)
   git worktree add ../project-feature-a feature-a
   git worktree add ../project-feature-b feature-b
   git worktree add ../project-refactor refactor-branch
   
   # 每个工作树运行独立的 Claude 实例
   cd ../project-feature-a && claude
   ```

3. **使用 Worktree 的好处**：

   - 彻底消除实例间的 Git 冲突。
   - 每个实例拥有干净、独立的工作目录。
   - 易于比较不同方案的输出结果。
   - 可对同一任务的不同实现方法进行基准测试 (Benchmark)。



### 5. 瀑布流工作法 (The Cascade Method)

管理多个 Claude Code 实例时的视觉与认知组织技巧：

- **布局**：新任务在右侧新建标签页打开。
- **流向**：保持从左到右（旧 -> 新）的一致性扫描方向。
- **专注度限制**：同时关注的任务不要超过 **3-4 个**。
  - *警示*：超过此数量，脑力切换的成本将超过并行带来的生产力提升。



💡claude中有tmux命令吗？和tasks命令有区别吗

> 这是一个非常敏锐的技术观察。简单来说：**Claude Code 本身并不内置 tmux，但它能直接调用你系统中的 tmux 命令；而 `/tasks` 是 Claude Code 内部的一套“任务管理抽象”。**
>
> 它们的关系就像是：**`tmux` 是一个外挂的“多线程工作台”，而 `/tasks` 是 Claude 自己的“记事本和调度表”。**
>
> 
>
> ### 1. Claude 中的 tmux
>
> Claude Code 实际上是运行在你的本地终端里的。这意味着只要你的电脑安装了 `tmux`，Claude 就可以通过执行 shell 命令来操作它。
>
> - **Claude 如何使用它：** 你可以对 Claude 说：“帮我开一个 tmux session 运行长耗时的测试，完成后把结果保存到 log.txt”。
> - **用途：** 主要用于**进程持久化**（比如你断开连接后程序继续跑）或**多窗口布局**。
>
> ### 2. Claude Code 的 `/tasks` 命令
>
> `/tasks` 是 Claude Code (一款由 Anthropic 开发的 CLI 终端助手) 的内置功能。它更像是一个 **Todo List + 状态机**。
>
> - **功能：** 允许你定义一个大的目标，并将其拆解为子任务（Subtasks）。
> - **特点：** 它可以记录哪些任务已完成，哪些正在进行。
>   - 它帮助 Claude 在复杂的开发流程中保持“不忘初心”，避免在解决 bug A 的过程中迷失在 bug B 里。
>
> ### 3. 核心区别对比
>
> | **特性**           | **tmux (终端复用器)**                        | **/tasks (Claude 任务管理)**                     |
> | ------------------ | -------------------------------------------- | ------------------------------------------------ |
> | **性质**           | 系统级的进程管理工具。                       | Claude Code 内置的逻辑组织工具。                 |
> | **主要解决的问题** | 防止程序因终端关闭而中断；分屏显示。         | 解决复杂任务的逻辑拆解和上下文追踪。             |
> | **Claude 的视角**  | Claude 把它看作一个可以操作的 **外部工具**。 | Claude 把它看作自己的 **工作计划表**。           |
> | **持久性**         | 重启电脑前有效。                             | 仅在当前 Claude Session 中有效（除非手动保存）。 |
>
> 
>
> ### 4. 为什么要强调“能在 tmux 解决就不要新开终端”？
>
> 这句话的深层含义是**上下文合并与隔离的平衡**。
>
> - **新开终端：** 相当于新开了一个“大脑”，新 Claude 实例完全不知道旧实例在干什么，你需要重复解释需求。
> - **在主会话用 tmux：** 主 Claude 实例依然是“大脑”。它在后台开启 tmux 就像是它伸出一只手去干杂活（比如查资料、跑编译），这只手干完活会直接向“大脑”汇报，**上下文是打通的**。
>
> #### 实际操作示例：
>
> > **User:** "我想优化这个接口，但在此之前，请先用 **tmux** 在后台运行现有的所有集成测试，如果有报错及时告诉我。同时，我们开始分析代码。"
>
> 在这种情况下，Claude 会利用 `tmux` 的后台特性实现“伪并行”处理，而不需要你手动去开第二个窗口折腾。

> 我们可以把你的主项目目录想象成一间房子。普通的 `git checkout` 就像是在房间里换家具，一次只能有一种风格；而 `git worktree` 则是**瞬间克隆出几间一模一样的样板房**，每间房互不干扰。
>
> ------
>
> ### 1. 为什么需要 `git worktree`？
>
> 在 Claude Code 的场景下，如果你在同一个文件夹里开两个 Claude 窗口：
>
> - **文件冲突**：Claude A 正在改 `User.py`，Claude B 同时也改了 `User.py`，保存时会互相覆盖。
> - **编译/依赖冲突**：Claude A 运行测试时产生的临时文件，可能会让 Claude B 的构建脚本报错。
> - **Git 状态混乱**：你在 A 窗口 commit 了，B 窗口的 git 索引就失效了。
>
> **使用 Worktree 后，每个 Claude 实例都有自己独立的物理文件夹。**
>
> ------
>
> ### 2. 逐行命令拆解
>
> #### A. 创建独立的工作空间
>
> Bash
>
> ```
> git worktree add ../project-feature-a feature-a
> ```
>
> - **`../project-feature-a`**：这是新文件夹的路径。它通常放在主项目目录的旁边。
> - **`feature-a`**：这是你要在新文件夹里操作的 Git 分支名。
> - **效果**：Git 会在主目录之外创建一个新文件夹，里面包含了该分支的所有文件。
>
> #### B. 进入并启动实例
>
> Bash
>
> ```
> cd ../project-feature-a && claude
> ```
>
> - 你进入了这个“平行时空”文件夹。
> - 启动 `claude`。此时这个 Claude 只能看到这个文件夹里的代码，它的修改、删除、测试操作**完全不会影响**你主目录里的代码。
>
> ------
>
> ### 3. 实战工作流示例
>
> 假设你正在开发一个商城系统：
>
> 1. **主目录 (Main)**：你正在修一个紧急 Bug。
> 2. **Worktree 1 (Feature A)**：你对 Claude 说：“去 `../shop-auth` 文件夹，帮我实现 OAuth 登录。”
> 3. **Worktree 2 (Refactor)**：你对另一个 Claude 说：“去 `../shop-cleanup` 文件夹，把所有的旧版注释换成 Docstring。”
>
> **你可以同时观察这两个 Claude 的进度：**
>
> - 一个在跑登录测试。
> - 一个在批量改格式。
> - **你自己**在主目录继续修 Bug。
>
> ------
>
> ### 4. 完成后的收尾 (重要)
>
> 并行开发结束后，你需要把成果合并回来并清理现场：
>
> 1. **提交代码**：在各个 Worktree 目录里让 Claude 完成 `git add` 和 `git commit`。
>
> 2. **回到主目录**：`cd ../main-project`。
>
> 3. **合并分支**：`git merge feature-a`。
>
> 4. **删除工作树**：
>
>    Bash
>
>    ```
>    git worktree remove ../project-feature-a
>    ```
>
>    *这会安全地删除那个临时文件夹，并让 Git 知道那个“平行时空”已经关闭了。*
>
> ------
>
> ### 5. 职业选手的小贴士
>
> - **配合 `/rename`**：启动 Claude 后，立即输入 `/rename [任务名]`。这样在 Claude Code 的会话列表里，你可以一眼看出哪个窗口在干哪件事。

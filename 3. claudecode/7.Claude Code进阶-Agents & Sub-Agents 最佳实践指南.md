## 1. 核心痛点：子智能体语境缺失 (The Context Problem)

**问题本质**：

Sub-agent 的存在是为了通过“返回摘要”来节省 Context Window（上下文窗口）。但 Orchestrator（编排者）拥有**语义语境（意图/原因）**，而 Sub-agent 往往只知道**字面查询**。

- **结果**：Sub-agent 返回的摘要虽然准确，但往往遗漏了 Orchestrator 真正需要的关键细节。

> **💡 职场类比 (@PerceptualPeak)**
>
> "就像老板（Orchestrator）派你去开会并要求汇报。你回来给了一个概要。十有八九老板会有追问。你的摘要无法包含他需要的所有信息，因为你没有他脑海里的那些隐含背景（Implicit Context）。"



## 2. 解决方案：迭代检索模式 (Iterative Retrieval Pattern)

为了解决语境缺失，不能期待一次性返回完美结果，而应建立**交互式循环**。

```
┌─────────────────┐
│  ORCHESTRATOR   │
│  (has context)  │
└────────┬────────┘
         │ dispatch with query + objective
         ▼
┌─────────────────┐
│   SUB-AGENT     │
│ (lacks context) │
└────────┬────────┘
         │ returns summary
         ▼
┌─────────────────┐      ┌─────────────┐
│   EVALUATE      │─no──►│  FOLLOW-UP  │
│   Sufficient?   │      │  QUESTIONS  │
└────────┬────────┘      └──────┬──────┘
         │ yes                  │
         ▼                      │ sub-agent
    [ACCEPT]              fetches answers
                                │
         ◄──────────────────────┘
              (max 3 cycles)
```



### 🔄 流程设计

1. **Dispatch (分发)**：Orchestrator 发送任务。
   - **关键技巧**：同时传递 `Query`（具体问题）+ `Objective`（宏观目标）。告诉 Sub-agent "做什么" 以及 "为什么做"，帮助其优化摘要重心。
2. **Return (返回)**：Sub-agent 返回摘要。
3. **Evaluate (评估)**：Orchestrator 检查信息是否满足目标。
4. **Follow-up (追问)**：如果不足，提出针对性追问（Sub-agent 回到源头获取答案）。
5. **Loop (循环)**：重复上述步骤，直到满足要求。
   - *限制：最大循环 3 次（防止死循环）。*



## 3. 落地架构：顺序阶段模式 (Sequential Phases)

```markdown
Phase 1: RESEARCH (use Explore agent)

- Gather context
- Identify patterns
- Output: research-summary.md

Phase 2: PLAN (use planner agent)

- Read research-summary.md
- Create implementation plan
- Output: plan.md

Phase 3: IMPLEMENT (use tdd-guide agent)

- Read plan.md
- Write tests first
- Implement code
- Output: code changes

Phase 4: REVIEW (use code-reviewer agent)

- Review all changes
- Output: review-comments.md

Phase 5: VERIFY (use build-error-resolver if needed)

- Run tests
- Fix issues
- Output: done or loop back
```

通过严格的阶段划分，确保每一步都有清晰的产出物。

| **阶段**         | **负责 Agent**  | **任务描述**                 | **关键产出 (Output)**   |
| ---------------- | --------------- | ---------------------------- | ----------------------- |
| **1. RESEARCH**  | Explore Agent   | 收集语境，识别模式           | `research-summary.md`   |
| **2. PLAN**      | Planner Agent   | 读取研究摘要，制定实施计划   | `plan.md`               |
| **3. IMPLEMENT** | TDD-Guide Agent | 读取计划，先写测试，再写代码 | 代码变更 (Code changes) |
| **4. REVIEW**    | Code-Reviewer   | 审查所有变更                 | `review-comments.md`    |
| **5. VERIFY**    | Build-Resolver  | 运行测试，修复错误           | 完成 (Done) 或 回滚     |

### ✅ 执行关键规则

- **输入/输出原则**：每个 Agent 接收**一个**清晰输入，产生**一个**清晰输出。
- **链式传递**：上一阶段的输出（Output）成为下一阶段的输入（Input）。
- **文件持久化**：中间产物（如计划、摘要）必须**存入文件**，而不仅是保留在内存中。
- **保持上下文清洁**：在 Agent 切换之间使用 `/clear` 命令。
- **严禁跳级**：每个阶段都增加特定价值，不可省略。



## 4. 策略分级：Agent 抽象层级 (Tier List)

建议从 Tier 1 开始，熟练后再尝试 Tier 2。

### 🟢 Tier 1: 直接增益 (Direct Buffs) - **推荐起步**

*易于使用，能显著提升稳定性。*

- **Sub-agents**：防止上下文腐烂（Context Rot），处理临时性专门任务。
- **Metaprompting (元提示)**：用 3 分钟编写提示词来完成 20 分钟的任务。提高稳定性并验证假设的合理性。
- **Ask User First**：在规划模式下，Agent 主动向用户提问以明确需求。

### 🔴 Tier 2: 高技术门槛 (High Skill Floor) - **需谨慎**

*高方差，调试困难，通常用于极复杂任务。*

- **Long-running Agents**：需权衡任务时长（15分钟 vs 4小时），调试过程漫长且昂贵。
- **Parallel Multi-agent (并行多智能体)**：方差极大。如果任务简单，花费在 Prompting 和合并冲突上的时间反而导致效率降低。
- **Role-based Multi-agent**：模型进化太快，硬编码的启发式角色难以维护且难以测试。
- **Computer Use Agents**：尚处于早期范式，需要大量人工干预（Wrangling）。
